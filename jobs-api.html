Jobs API

This document gives the design, the flows, and the key decisions for the Jobs API.

1 Purpose

The Jobs API keeps the status of one job.

A client uploads the input files.

The client then starts the job.

The worker calls an agent.

The agent reads the input files.

The agent writes the output files.

A status page reads the job status until the work stops.

Note — The sentences in this document follow ASD-STE100. Each sentence has one idea. The same word has the same meaning in each section.

2 Technical names

NameMeaning
WorkerThe program that supplies the Jobs API.
JobOne unit of work. Each job has one id.
ClientThe web backend that uploads files and starts the job.
AgentThe Cursor automation that does the work.
BucketThe R2 store with the name jobs.
ObjectOne file in the bucket.
RowThe one D1 record for the job.
TokenThe secret JOBS_TOKEN. The client, the agent, and the worker keep the same secret.
Automation tokenThe value automation.auth. This token is only for the call from the worker to the agent.
Presigned URLA URL that gives read access to one object for 300 seconds.
Event streamAn open HTTP response. The status page reads status events from this response.
EventSourceThe browser object that opens an event stream. It cannot set an Authorization header.
MCPThe HTTP endpoint. The agent uses this endpoint to report status.
Relative pathA file name under the job folder. Example: in/notes.txt.

3 Parts

Four parts do the work.

  • Client. The client sends files and starts the job. The client also downloads the output files.
  • Worker. The worker checks the token, writes objects, keeps the row, and calls the agent.
  • Bucket. The bucket keeps the input objects and the output objects.
  • Agent. The agent reads input objects, writes output objects, and reports status.

The status page is not a fifth part of the API. The page only reads the event stream.

The client supplies the job id. The id must be a UUID. The worker rejects every other id.

4 Routes

All paths are on the worker. {filename} is one path segment. The name must not be . or ... The name must not contain / or \.

MethodPathSenderResult
POST /jobs/{id}/in/{filename} Client The worker stores the body at {id}/in/{filename}. The response is 201 and { name, size }. name is in/{filename}.
GET /jobs/{id}/in Agent or client The worker sends { files: [{ name, size }] } for the objects under {id}/in/.
GET /jobs/{id}/in/{filename} Agent The worker sends 302. Location is a presigned URL for that object.
POST /jobs/{id}/out/{filename} Agent The worker stores the body at {id}/out/{filename}. The response is 201 and { name, size }. name is out/{filename}.
GET /jobs/{id}/out Client After success, the worker sends the file list from the row.
GET /jobs/{id}/out/{filename} Client After success, the worker sends 302 to a presigned URL for that output file.
POST /jobs/{id} Client The body is JSON. The worker creates the row and calls the agent.
GET /jobs/{id} Client The worker sends { id, status, message }. The response has an ETag.
GET /jobs/{id}/events Status page The worker sends the event stream. This route has no token.
POST /jobs/{id}/mcp Agent The agent calls the tools progress, success, or fail.

5 Flows

5.1 Upload the input files

  1. Step 1

    The client sends POST /jobs/{id}/in/{filename} with the token.

  2. Step 2

    The worker writes the request body to the bucket. The worker does not keep the bytes in the row.

  3. Step 3

    The worker sends 201 and { name, size }.

  4. Step 4

    The client repeats steps 1 to 3 for each input file.

This flow is valid only before the row exists. If the row exists, the worker sends 409.

5.2 Start the job

  1. Step 1

    The client sends POST /jobs/{id}. The content type is application/json.

  2. Step 2

    The body contains actor and automation. automation contains auth and url.

  3. Step 3

    url must use https. The body can also contain amount and currency.

  4. Step 4

    If amount is present and currency is absent, the worker stores ARS.

  5. Step 5

    If the currency is USD, amount must be an integer. That integer is a number of cents.

  6. Step 6

    The worker reads the input objects. The worker inserts the row. The status is queued. The message is null.

  7. Step 7

    The worker sends POST to automation.url. The header is Authorization: Bearer and the automation token.

  8. Step 8

    The JSON body contains actor, id, input, and mcp. input is a list of relative paths. Example: in/notes.txt.

  9. Step 9

    If that call fails, the worker sets the status to failed and sends 502 to the client.

  10. Step 10

    If the call succeeds, the status stays queued. The worker sends 201.

A second start for the same id gets status 409. The worker does not store the automation token.

5.3 Read inputs and write outputs

  1. Step 1

    The agent sends GET /jobs/{id}/in with the token. The worker sends the input file list.

  2. Step 2

    The agent sends GET /jobs/{id}/in/{filename} with the token.

  3. Step 3

    If the object exists, the worker sends 302. The Location value is a presigned URL. The URL is valid for 300 seconds.

  4. Step 4

    The agent reads the object from that URL. That read does not use the jobs token.

  5. Step 5

    The agent sends POST /jobs/{id}/out/{filename} with the token and the file body.

  6. Step 6

    The worker writes the body to {id}/out/{filename}. This request is valid only when the status is queued or running.

5.4 Report status

The agent sends POST /jobs/{id}/mcp with the token. The body is one JSON-RPC message. The protocol is 2026-07-28.

The endpoint has three tools.

  • progress(message) sets the status to running and stores the message. The first call also stores the start time.
  • success(message, files) sets the status to done. files is a list of { name, size }. Each name has the form out/{filename}. The object for each name must be in the bucket before this call.
  • fail(message) sets the status to failed and stores the message.

If the status is done or failed, a tool call does not change the row. The tool result is an error.

5.5 Wait, then download

  1. Step 1

    The status page opens GET /jobs/{id}/events. This request has no token.

  2. Step 2

    The worker reads the row and writes one event. The event data is { id, status, message }.

  3. Step 3

    If the status is not done and the status is not failed, the worker writes a ping line. The worker waits 1.5 seconds. The worker then repeats from step 2.

  4. Step 4

    If the status is done or failed, the worker closes the stream. A missing row also closes the stream.

  5. Step 5

    If the connection stops, the page opens the stream again. The row has the full status. There is no event log.

  6. Step 6

    A client can send GET /jobs/{id} with the token. The response is the same JSON. The ETag is the updated time of the row.

  7. Step 7

    If If-None-Match is that ETag, the worker sends 304 and no body.

  8. Step 8

    After success, the client sends GET /jobs/{id}/out. The worker sends the file list from the row.

  9. Step 9

    The client sends GET /jobs/{id}/out/{filename}. The worker sends 302 to a presigned URL. The URL is valid for 300 seconds.

If the status is not done, a request for the output list or for one output file gets status 409.

6 Key decisions

01
The worker writes every file

The client and the agent do not write to the bucket. They send the bytes to the worker. The worker writes the object. The bucket key stays on the worker.

02
A download is a short redirect

A GET for one file does not send the file bytes through the worker. The worker sends 302 to a presigned URL. The URL is valid for 300 seconds. The response also has cache-control: no-store.

03
No temporary bucket credentials

The agent does not receive an access key. The agent sends the jobs token to the worker. The worker signs each download URL with its bucket key.

04
Two tokens, two jobs

The jobs token gives access to the worker. The automation token gives access to the Cursor automation. The worker does not send the jobs token to the automation URL.

05
The event stream has no token

A browser EventSource cannot send an Authorization header. The event stream is open to a caller who knows the id. The id is a random UUID. A person who does not know the id cannot open the stream.

06
One row is the full status

The worker replaces the row. The worker does not keep an event log. A new stream reads the same row. Amount, currency, and the file list are not in the public status.

07
Input list and output list differ

GET /jobs/{id}/in lists the objects in the bucket. GET /jobs/{id}/out lists the files that success stored on the row. An output object that success did not name is not in that list.

08
The file set freezes at the correct time

The client cannot upload an input file after the row exists. The input list for the start call does not change after that time. The agent can upload an output file only when the status is queued or running.

09
A failed start is visible

If the call to the agent fails, the worker sets the status to failed. The worker stores a short message. The event stream can then close. The status does not stay queued.

7 The row

The worker keeps one row for each job. A new status replaces the old status.

FieldContent
idThe job UUID.
actorThe actor string from the start request.
statusqueued, then running, done, or failed.
messageNull at the start. A tool call or a failed start replaces it.
amountA number, or null. For USD, the number is cents.
currencyARS or USD when amount is set. Otherwise null.
filesThe JSON list from success. Each name has the form out/{filename}.
created, updatedTimes in epoch milliseconds. updated is the ETag.
startedThe time of the first progress call. Otherwise null.

The public JSON and the event stream contain only id, status, and message.

8 Access

Each request to the worker, except the event stream, must send Authorization: Bearer and the jobs token.

The worker compares that value with its own secret. A missing token or a different token gets status 403.

The worker, the agent, and the client have the same secret.

The automation token is not that secret. The worker puts the automation token in the Authorization header of the call to automation.url.

OPTIONS has no token. The worker permits GET, POST, and OPTIONS from other origins.

Status codes —

201 means the worker stored a file, or the worker started the job. 302 means a presigned download. 304 means the status is the same. 400 means the body or the file name is not valid. 403 means the token does not match. 404 means the job, the route, or the object is absent. 409 means the job state does not permit the request. 415 means the start body is not JSON. 502 means the call to the agent failed.
