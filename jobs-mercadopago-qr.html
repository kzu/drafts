MercadoPago QR for paid jobs

ARS-priced jobs no longer kick off Cursor immediately. The Jobs API creates a MercadoPago dynamic QR order, holds the job in pending, and only enqueues the automation after MercadoPago reports order.processed.

1. Summary

Before this change, POST /jobs/{id} always wrote status queued and POSTed the Cursor automation webhook in the same request. Optional amount / currency were stored on the D1 row and never used.

Now payment is a gate for ARS amounts:

  • No amount — free job: create → kickoff Cursor → queued (same response as before).
  • Amount in ARS — create MercadoPago QR order → pending + return qr → wait for webhook → kickoff → queued.
  • USD — rejected with 400 Invalid currency. Only unpaid or ARS-paid jobs are supported.
Names kept on purpose queued, running, done, and failed are unchanged. Only created and pending were added ahead of work.

2. Status model

created

Row just inserted. Brief; free jobs leave it immediately, paid jobs move to pending after the MP call.

pending

Waiting for payment (or, later, other HITL). QR is available on GET/SSE. Cursor is not called yet.

queued

Automation kickoff succeeded. Same meaning as before.

running

Agent called MCP progress.

done

Agent called MCP success. Outputs downloadable.

failed

Kickoff failed, payment canceled/expired, or agent fail.

3. Flows

Free job (no amount)

created → kickoff Cursor → queued → MCP → done | failed

Paid job (ARS amount)

created → MP order → pending + QR → webhook order.processed → kickoff → queued → …

Paid path in detail

  1. Client Uploads inputs to POST /jobs/{id}/in/…, then starts with amount (and optional currency: "ARS").
  2. Worker Inserts the row as created, stores automation URL/token/agent for later, calls MercadoPago POST /v1/orders with type: "qr" and config.qr.mode: "dynamic".
  3. Response Returns 201 { id, status: "pending", qr }. qr is the EMVCo string from type_response.qr_data — the client renders it as a QR image for the buyer.
  4. Buyer Scans with the MercadoPago app and pays.
  5. MercadoPago POSTs to https://jobs.chebot.si/webhooks/mercadopago with action order.processed.
  6. Worker Verifies x-signature, resolves the job via external_reference (the job UUID) or mp_order_id, kicks off Cursor with the stored automation credentials, clears those secrets, sets status queued.
  7. Agent Runs as before: MCP progress / success / fail.

4. API surface

Start job — POST /jobs/{id}

BodyResult
No amount 201 { id, status: "queued" } after successful Cursor kickoff
amount (ARS, default currency) 201 { id, status: "pending", qr: "…" } — Cursor not called yet
currency: "USD" 400 { error: "Invalid currency." }
MP create fails 502, job marked failed

Public status

GET /jobs/{id} and the SSE stream include qr only while status === "pending", so a status page can refresh the code without holding secrets. Amount, currency, and automation credentials stay off the public payload.

Webhook — POST /webhooks/mercadopago

  • No JOBS_TOKEN (MercadoPago cannot send it).
  • Requires valid x-signature / x-request-id / data.id HMAC against MP_WEBHOOK_SECRET.
  • order.processed → enqueue automation (idempotent if already past pending).
  • order.canceled / order.expired → failed with a clear message, only if still pending.
  • Always acknowledges with 200 after handling (or 401 on bad signature).

MCP gate

Agent tools reject created / pending with “Job is not ready.” Work tools still require queued or running.

Automation credentials are stored until kickoff succeeds, then nulled so they do not linger on paid or free jobs.

MercadoPago create uses job UUID as external_reference and as X-Idempotency-Key, so retries do not mint duplicate orders for the same job.

6. Your MercadoPago checklist

Still on you — not done in code

The Worker is ready to call the Orders API and receive webhooks. You still need a seller application, a store + cash register (external_pos_id), production credentials, and a webhook URL pointed at jobs.

  1. 1. Application in Your integrations

    Open MercadoPago Developers → Your integrations and use (or create) the application that will own QR Code / Orders. Prefer production credentials for real money; use test credentials (Access Token starts with APP_USR) while developing.

  2. 2. Create store and cash register (caja)

    QR Orders require a store and a POS/caja with an external_id you choose. That value becomes MP_EXTERNAL_POS_ID in the Worker (config.qr.external_pos_id). Follow QR Code → prerequisites / configure sucursal y caja. Without this, POST /v1/orders fails and paid jobs go failed.

  3. 3. Copy Access Token

    From the app → Integration data → Credentials (test or production). This is MP_ACCESS_TOKEN. Never put it in client-side code or the repo.

  4. 4. Configure the Order webhook

    In the same app: Webhooks → Configure notifications. Production URL: 

    https://jobs.chebot.si/webhooks/mercadopago

    Subscribe to the event named Order (Mercado Pago) (topic orders). Save, then copy the generated secret signature — that is MP_WEBHOOK_SECRET.

    Docs: Configure orders notifications.

  5. 5. Simulate a notification

    In the Webhooks UI, use Simulate notification with a real ORD… id from a test order (or the id from a pending job’s mp_order_id). Confirm the Worker returns 200. A bad secret yields 401.

  6. 6. End-to-end with a test buyer

    Create a paid job against test credentials, render the returned qr string as a QR image, pay with a buyer test account in the MercadoPago app, and watch the job leave pending for queued (and Cursor kickoff).

What the Worker sends to MercadoPago 
POST https://api.mercadopago.com/v1/orders
Authorization: Bearer <MP_ACCESS_TOKEN>
X-Idempotency-Key: <job-uuid>

{
  "type": "qr",
  "total_amount": "1500.00",
  "description": "Job <job-uuid>",
  "external_reference": "<job-uuid>",
  "config": {
    "qr": {
      "external_pos_id": "<MP_EXTERNAL_POS_ID>",
      "mode": "dynamic"
    }
  },
  "transactions": { "payments": [{ "amount": "1500.00" }] },
  "items": [{ "title": "<actor>", "unit_price": "1500.00",
              "quantity": 1, "unit_measure": "unit",
              "external_code": "<job-uuid>" }]
}
Response field used: type_response.qr_data (EMVCo payload for your QR renderer).
QR signature note from MercadoPago docs Some QR documentation says Order webhooks for QR cannot always be verified with the secret signature the same way as other products. The Worker still validates x-signature as documented for Order notifications. If simulations fail signature checks in production QR, open a MercadoPago support ticket — they document that path explicitly — or temporarily diagnose with the simulate tool and GET /v1/orders/{id} confirmation (the handler already GETs the order when the body is thin).

7. Cloudflare / D1 you still need

  1. Apply the D1 migration

    On the existing jobs database, run jobs/migrations/0001_payment.sql (or recreate from updated schema.sql in a fresh DB). Without these columns, inserts fail at runtime.

  2. Set Worker secrets / vars

    In the jobs Worker:

    NameRole
    MP_ACCESS_TOKENBearer for Orders API
    MP_WEBHOOK_SECRETHMAC key from Webhooks config
    MP_EXTERNAL_POS_IDCaja external_id / POS id

    Example: npx wrangler secret put MP_ACCESS_TOKEN (and the other two) from the jobs/ directory. MP_EXTERNAL_POS_ID can be a plain [vars] entry if you prefer it non-secret.

  3. Deploy the Worker

    Deploy so https://jobs.chebot.si/webhooks/mercadopago is live before you save the webhook URL in MercadoPago.

8. How to test locally

cd jobs
npm test

Coverage includes: free enqueue still hits Cursor; ARS amount hits MP and stays pending; USD rejected; signed order.processed unlocks kickoff and is idempotent; cancel/expire → failed; bad signature → 401.

Manual smoke after deploy

  1. Upload an input, POST /jobs/{id} with amount: 100.
  2. Expect pending + qr. Confirm status GET also returns qr.
  3. Pay (test buyer) or simulate webhook with that order id.
  4. Expect status queued and a Cursor automation invocation.

9. Caveats

  • Client must render qr (EMVCo string) into a QR image — the API does not return a PNG.
  • Default MP order expiration is short (on the order of minutes unless you later pass expiration_time). Expired orders fail the job if still pending.
  • Input uploads remain forbidden once the row exists — same as before — so upload first, then start (and pay).
  • HITL approval beyond payment is not implemented; pending is the status reserved for that class of waits.
  • Refunds / order.refunded are not handled yet (ack only / no status change beyond ignore).
