1. The scene we’re aiming for

User → Muse

“Tengo esta planilla de un juicio laboral. Calculame los intereses con la tasa pasiva BCRA y mandame el resultado.”

Muse lists Intereses laborales (ARS 1.500 / archivo), confirms the quote, takes the spreadsheet from chat or Dropbox, asks once for payment approval, kicks the job, streams progress, then hands back the ZIP — all inside Muse.

That is not “open ipcmas3.ar in a browser tab.” Muse already browses. A connector earns its keep by finishing the task: catalog → quote → pay → run → deliver.

2. What we already have

Jobs engine

Cloudflare Worker at jobs.chebot.si now owns the paid path. An ARS amount creates a Mercado Pago QR order plus a checkout link, holds the job at pending, and starts the automation only after order.processed. Free jobs (no amount) still kick the webhook immediately. USD is rejected.

IPC+3 product shell

ipcmas3 still picks the process (one catalog entry, intereses-laborales), uploads the spreadsheet, and downloads the ZIP. Payment is no longer a parked MODO panel: it sends name: "IPC+3 - 1 Archivo" and amount (env JOB_AMOUNT, default 1500) and shows pay.qr / pay.link until the job leaves pending.

The compute path and the Argentina checkout now live in one service. A Muse connector can reuse that enqueue. What it still has to invent is a chat-native way to finish payment, because a QR and an external checkout link are exactly the handoff Muse’s review rejects.

Lifecycle the connector can already call Upload inputs, then POST /jobs/{id} returns 201 with created before Mercado Pago finishes. Poll until pending exposes pay, or until failed. After payment the status becomes queued. Cancel with DELETE only while created or pending.

3. What Muse’s platform demands

From Meta’s Connector guidelines and the submission flow at muse.ai/platform:

  • Complete the task in Muse. Search → price → authorize → checkout → confirmation. Sending the user away to finish payment fails review.
  • Beat the browser. A thin wrapper over ipcmas3.ar is not enough; account access, reliable actions, or fewer steps must show.
  • Hosted MCP or Raw API. Submit a live HTTPS endpoint, docs, auth (API key or OAuth + PKCE / DCR), test account, business verification, data-processing questionnaire.
  • Tool classes. Read / write / sensitive write. Payment and “start processing” are sensitive writes — Ask every time, never “Always allow.”
  • Transactions (§4.7). Before charge: seller, full price + currency, terms, refund policy. Distinguish quoted / pending / confirmed / failed. Prevent duplicate charges. Receipts + support path.
  • Stripe Link partnership. Muse markets Link for connector payments. Users approve the total in chat; Muse never sees card details.

Practically: we submit something like “IPC+3” or “Chebot Jobs” as an Existing MCP connector, with OAuth for the user’s account and a second MCP surface that is not the agent-facing /mcp used by Cursor automations.

4. The gap map

Biggest product tension Jobs payment is Mercado Pago in ARS: a dynamic QR plus an init_point checkout. That matches ipcmas3.ar. Muse’s transaction rules want the purchase finished inside the chat, and their partner story is Stripe Link. Handing Muse pay.qr or pay.link and waiting is the web flow, not a connector that will pass review.

5. Proposed Muse-facing tool surface

Separate endpoint, e.g. https://jobs.chebot.si/muse/mcp or https://ipcmas3.ar/api/muse/mcp. Host it where the catalog, pricing, and payment already live — today that’s closer to ipcmas3 than to the raw jobs Worker.

Tool Class Job
list_processes Read Return process id, name, description, accept types, max size, price, currency, refund blurb.
quote_job Read Given process + file metadata, return seller, ARS total, and terms. No Mercado Pago call yet.
create_job Write Upload bytes, then enqueue with name, amount, and the hidden automation. Poll past created.
start_paid_job Sensitive The Muse-shaped charge. Today the service only knows how to emit pay.qr and pay.link — this tool has to wrap a checkout Muse can complete, or it is just a QR relay.
get_job Read Pass through status and message. While pending, the snapshot already has pay.qr and pay.link. Hide automation credentials; they are cleared after kickoff anyway.
download_result Read When done, return a short-lived URL (or bytes) for each out/… file Muse can fetch and give the user.
cancel_or_refund Sensitive Only if we offer it on the web; Muse guidelines want parity for supported follow-ups.

Happy path as Muse sees it

  1. Step 1 · Discover list_processes → “Intereses laborales — ARS 1.500 / archivo — .xlsx/.xls/.ods ≤ 200 KB.”
  2. Step 2 · Intake User attaches the spreadsheet. create_job uploads it and enqueues with amount. The worker answers created immediately; Mercado Pago order creation continues in the background.
  3. Step 3 · Approve pay On the web, the next poll is pending with a QR and a checkout link, and the automation stays parked until Mercado Pago posts order.processed. In Muse that step has to become an in-chat approval, not “scan this QR.”
  4. Step 4 · Wait After payment, status is queued, then running, then done or failed. A cancel or expiry webhook marks the job failed (“Payment canceled.” / “Payment expired.”). DELETE only works before that, while the job is still created or pending.
  5. Step 5 · Deliver download_result → Muse presents the ZIP. Receipt + support link in the confirmation text.

6. Payment: three realistic tracks

A

Keep Mercado Pago for the web

This is what shipped. ipcmas3 shows the QR and the checkout link. The jobs webhook is the source of truth: pay, then automate. Do not ask Muse to scan that QR.

B

A second pay rail for Muse

Jobs currently accepts only ARS and always opens Mercado Pago when amount is set. A Muse path needs either a new currency/provider on the worker, or a connector that charges with Stripe Link and then enqueues with no amount (automation starts at once) after its own webhook says paid. The second option reintroduces a pay-then-run split the worker just collapsed.

C

Paid job, caller finishes the work

Enqueue may omit automation when amount is set. After order.processed the status becomes queued and nobody is called. The caller then PATCHes done or failed. Useful if Muse’s own tools did the processing — a poor fit for IPC+3, whose value is the Cursor automation.

Recommendation: leave Track A as the ipcmas3 path. For Muse, add an explicit paid-without-Mercado-Pago enqueue (or a provider field) so Link can unlock the same automation webhook. Until that exists, the connector cannot both charge in chat and reuse the worker’s payment gate.

7. Build plan (what it would take)

Phase 0 — Decide the product border

  • Brand the connector as IPC+3 (one process, sharp value) vs a generic Chebot Jobs multi-process platform.
  • IPC+3 is the faster story: one catalog entry, known price, known automation, existing privacy/terms pages.
  • Generic jobs needs a public process registry API that doesn’t exist yet.

Phase 1 — Consumer MCP in front of jobs

  • New hosted MCP with the tools above. OAuth can still be the ipcmas3 account, but enqueue goes to the jobs API the same way enqueueJob does: file, then name + actor + automation + amount.
  • Do not surface the agent MCP (progress / success / fail) or the stored automation token.
  • Map the Muse user to actor. The jobs row has no per-user auth of its own — the shared JOBS_TOKEN stays server-side.
  • Lengthen or refresh download URLs so Muse can fetch after the chat round-trip (today’s 300s presign may be tight).

Phase 2 — A pay gate Muse is allowed to finish

  • Do not expose pay.link as the completion step. Mercado Pago stays the AR web checkout.
  • Add a worker mode that records a paid ARS (or USD) job without creating a Mercado Pago order, unlocked by a connector webhook the same way order.processed unlocks automation today.
  • Keep idempotency: a second pay notification must not double-kick. The current webhook already no-ops once status has left pending.
  • Sandbox credentials for Muse reviewers, with a note on how to reach queued without a real charge.

Phase 3 — Platform intake

  • Icon 512×512, example prompts, privacy + terms URLs, support contact.
  • Submit at muse.ai/platform → Existing MCP → portal: business verification, data questionnaire, credentials, dedicated test account with a sample spreadsheet.
  • Annotate every tool Read/Write/Sensitive in the docs (portal annotation “coming soon”).

Phase 4 — Hardening that review will poke

  • Duplicate-charge prevention (key on submission / payment intent id).
  • Never claim success until jobs status is done and outputs exist.
  • Retention/deletion story for uploaded spreadsheets (legal files — sensitive).
  • Rate limits and abuse caps aligned with free-tier logic.
Rough effort (order of magnitude) The upload, poll, cancel, and download path is done. What remains for an IPC+3 connector is the Muse MCP plus one pay-unlock that is not Mercado Pago. Review and regional policy still dominate the calendar.

8. Open questions to settle before coding

IPC+3 brand or Chebot Jobs platform?

One sharp process ships faster and features better. Multi-process needs a catalog service first.

Where does the Muse MCP live?

Payment, status, and kickoff now live on the jobs worker. The Muse MCP should sit in front of that API, not on /mcp — that endpoint is still the agent reporting channel and shares JOBS_TOKEN.

Second payment provider, or enqueue-after-external-pay?

The worker rejects USD and treats any amount as Mercado Pago. Muse needs a way to mark a job paid without a QR. That is a small API change, not a new jobs service.

How does Muse hand us the file?

Need to verify current Muse file-attachment / Dropbox-connector patterns for MCP inputs during a prototype against a test listing — don’t assume base64 forever.

Guest checkout?

Guidelines prefer guest checkout when the product has it. Today ipcmas3 requires Google sign-in; either add guest Muse accounts or disclose “account required.”

Bottom line

File in, ARS price, Mercado Pago, automation, file out — that loop is live on jobs.chebot.si, and ipcmas3 already speaks it. Muse still needs its own front door: a consumer MCP, a pay signal that is not a QR, and Meta’s review packet. The worker should keep owning “paid, then run.” The connector should not reimplement checkout by pasting pay.link into the chat.
