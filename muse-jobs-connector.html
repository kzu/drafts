1. The scene we’re aiming for

User → Muse

“Tengo esta planilla de un juicio laboral. Calculame los intereses con la tasa pasiva BCRA y mandame el resultado.”

Muse lists Intereses laborales (ARS 1.500 / archivo), confirms the quote, takes the spreadsheet from chat or Dropbox, asks once for payment approval, kicks the job, streams progress, then hands back the ZIP — all inside Muse.

That is not “open ipcmas3.ar in a browser tab.” Muse already browses. A connector earns its keep by finishing the task: catalog → quote → pay → run → deliver.

2. What we already have

Jobs engine

Cloudflare Worker at jobs.chebot.si: R2 for bytes, D1 for status, shared JOBS_TOKEN, kickoff to a Cursor automation, agent MCP tools progress / success / fail, public SSE for waiting, presigned downloads when done. Amount and currency are stored on the row — but payment is not collected here.

IPC+3 product shell

The front-end at ipcmas3 owns the human journey: Google sign-in, tool catalog (intereses-laborales), upload, MODO QR pay-per-file (currently parked), free/beta tiers, then enqueueJob into the jobs service and download the ZIP.

So the hard compute path — spreadsheet in, agent out, status stream, file download — already exists. What Muse needs is a consumer-facing façade: pick a process, price it, charge for it, and return the result without leaking automation secrets.

Reuse, don’t rebuild Keep the jobs Worker as the durable run store. Muse should never see AGENT_URL / AGENT_TOKEN. The connector (or ipcmas3 server) owns automation kickoff the same way the web app does today.

3. What Muse’s platform demands

From Meta’s Connector guidelines and the submission flow at muse.ai/platform:

  • Complete the task in Muse. Search → price → authorize → checkout → confirmation. Sending the user away to finish payment fails review.
  • Beat the browser. A thin wrapper over ipcmas3.ar is not enough; account access, reliable actions, or fewer steps must show.
  • Hosted MCP or Raw API. Submit a live HTTPS endpoint, docs, auth (API key or OAuth + PKCE / DCR), test account, business verification, data-processing questionnaire.
  • Tool classes. Read / write / sensitive write. Payment and “start processing” are sensitive writes — Ask every time, never “Always allow.”
  • Transactions (§4.7). Before charge: seller, full price + currency, terms, refund policy. Distinguish quoted / pending / confirmed / failed. Prevent duplicate charges. Receipts + support path.
  • Stripe Link partnership. Muse markets Link for connector payments. Users approve the total in chat; Muse never sees card details.

Practically: we submit something like “IPC+3” or “Chebot Jobs” as an Existing MCP connector, with OAuth for the user’s account and a second MCP surface that is not the agent-facing /mcp used by Cursor automations.

Biggest product tension IPC+3 prices in ARS via MODO. Muse’s payment story is Stripe Link and currently US-consumer oriented. A Muse launch may need USD pricing + Stripe first, with MODO remaining the Argentina web path — or wait until Muse/Link covers AR markets.

5. Proposed Muse-facing tool surface

Separate endpoint, e.g. https://jobs.chebot.si/muse/mcp or https://ipcmas3.ar/api/muse/mcp. Host it where the catalog, pricing, and payment already live — today that’s closer to ipcmas3 than to the raw jobs Worker.

Tool Class Job
list_processes Read Return process id, name, description, accept types, max size, price, currency, refund blurb.
quote_job Read Given process + file metadata (rows/size), return seller, total, currency, terms. No charge.
create_job Write Accept file (or reference), bind process, create submission + jobs input upload. Status awaiting_payment or queued if free/beta.
start_paid_job Sensitive Charge the quoted amount via Muse/Stripe path, then enqueue automation. Idempotent on submission id.
get_job Read Map jobs status (queued/running/done/failed) + progress message. Never return tokens.
download_result Read When done, return a short-lived URL (or bytes) for each out/… file Muse can fetch and give the user.
cancel_or_refund Sensitive Only if we offer it on the web; Muse guidelines want parity for supported follow-ups.

Happy path as Muse sees it

  1. Step 1 · Discover list_processes → “Intereses laborales — ARS 1.500 / archivo — .xlsx/.xls/.ods ≤ 200 KB.”
  2. Step 2 · Intake User attaches the spreadsheet (or Muse pulls it from Dropbox). create_job stores bytes and returns a quote + job id.
  3. Step 3 · Approve pay Muse shows seller, total, terms. User Allow-once on start_paid_job. Charge confirms → enqueue with amount/currency on the jobs row.
  4. Step 4 · Wait Poll get_job until done / failed. Progress messages from the agent MCP stay internal; surface the public message.
  5. Step 5 · Deliver download_result → Muse presents the ZIP. Receipt + support link in the confirmation text.

6. Payment: three realistic tracks

A

Stripe / Link first (Muse-native)

Add a USD (or multi-currency) price for Muse users. Use Stripe Checkout or PaymentIntents in a way Muse’s Link wallet can complete in-chat. Matches Meta’s partner story and review checklist. Web ARS/MODO stays as-is.

B

Guest or prepaid credits

Sell packs outside Muse; connector only burns a credit (still a sensitive write, but no card). Weaker “complete the purchase” story if Muse expects checkout — fine for beta review if disclosed.

C

MODO inside Muse

Unlikely to satisfy “finish checkout in Muse” while QR wallets live outside chat. Keep MODO for ipcmas3.ar; don’t bet the connector on it.

Recommendation: Track A for the Muse connector, with clear regional disclosure (“available where Link/Stripe works”). Keep the jobs row’s amount/currency as the ledger Muse and the web both write into after payment confirms.

7. Build plan (what it would take)

Phase 0 — Decide the product border

  • Brand the connector as IPC+3 (one process, sharp value) vs a generic Chebot Jobs multi-process platform.
  • IPC+3 is the faster story: one catalog entry, known price, known automation, existing privacy/terms pages.
  • Generic jobs needs a public process registry API that doesn’t exist yet.

Phase 1 — Consumer MCP on top of ipcmas3

  • New hosted MCP with the tools above; OAuth against the same user accounts as the site (or Muse OAuth client → map to user id).
  • Reuse createSubmission / processSubmission / enqueueJob — don’t duplicate kickoff.
  • Map ownership: Muse user ↔ owner_user_id ↔ jobs actor.
  • Lengthen or refresh download URLs so Muse can fetch after the chat round-trip (today’s 300s presign may be tight).

Phase 2 — Payment that Muse can finish

  • Stripe path for Muse quotes; webhook → mark submission paid → enqueue (idempotent).
  • Document refund/support policy; implement at least status + receipt tools.
  • Sandbox mode for Muse reviewers (no real charges), called out in the test-user notes.

Phase 3 — Platform intake

  • Icon 512×512, example prompts, privacy + terms URLs, support contact.
  • Submit at muse.ai/platform → Existing MCP → portal: business verification, data questionnaire, credentials, dedicated test account with a sample spreadsheet.
  • Annotate every tool Read/Write/Sensitive in the docs (portal annotation “coming soon”).

Phase 4 — Hardening that review will poke

  • Duplicate-charge prevention (key on submission / payment intent id).
  • Never claim success until jobs status is done and outputs exist.
  • Retention/deletion story for uploaded spreadsheets (legal files — sensitive).
  • Rate limits and abuse caps aligned with free-tier logic.
Rough effort (order of magnitude) For an IPC+3-scoped connector with Stripe sandbox: on the order of days to a couple of weeks if the existing submission/jobs path stays stable — not a greenfield rewrite. The schedule risk is almost all payment + regional policy + Muse review, not R2 uploads.

8. Open questions to settle before coding

IPC+3 brand or Chebot Jobs platform?

One sharp process ships faster and features better. Multi-process needs a catalog service first.

Where does the Muse MCP live?

ipcmas3 already owns auth, catalog, payment, and enqueue. The jobs Worker should stay the run engine — adding Muse tools there would mix agent MCP with consumer MCP under one token model.

ARS/MODO vs USD/Stripe?

If Muse users are primarily US Link wallets, ship USD. Keep MODO for the Argentine web app.

How does Muse hand us the file?

Need to verify current Muse file-attachment / Dropbox-connector patterns for MCP inputs during a prototype against a test listing — don’t assume base64 forever.

Guest checkout?

Guidelines prefer guest checkout when the product has it. Today ipcmas3 requires Google sign-in; either add guest Muse accounts or disclose “account required.”

Bottom line

The jobs Worker already does the expensive part. Muse is mostly a new front door: a consumer MCP, real in-chat payment, and the paperwork Meta’s review expects. Mirror the ipcmas3 journey in tools, keep the Cursor automation behind the server, and pick Stripe/Link for the connector even if the website keeps MODO.
